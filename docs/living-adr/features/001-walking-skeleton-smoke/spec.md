# Feature Specification: walking-skeleton-smoke

## Overview
Feature 001 proves the thinnest visible LivingADR path across the planned two-deployable architecture: replay or receive one merged-PR-like event, classify it with a deterministic stub, create a minimal `ADRDraft`, accept it through a stubbed HITL action, persist a stub approved `ADRRecord`, and answer one MCP-style `answer_why` query from approved seeded context.

This is intentionally a walking skeleton, not production intelligence. It validates integration seams across `workflow-service`, graph persistence, HITL, and `mcp-context-server` without production classifiers, Claude drafting quality, real GitHub webhooks, durable approval enforcement, or production graph semantics.

## User Stories

### [US-1] Replay a merged-PR-like event — Priority: P1
**As a** LivingADR developer, **I want** a deterministic replay fixture or local receive path for one merged-PR-like event, **so that** the end-to-end workflow can be demonstrated before real GitHub webhook infrastructure exists.

#### Acceptance Scenarios
- **Given** a seeded merged-PR-like fixture with repository identity, PR metadata, and small diff summary, **When** the smoke replay command or endpoint runs, **Then** the workflow receives exactly one normalized `SCMEvent` scoped to that repository.
- **Given** the same fixture is replayed twice, **When** the skeleton handles the duplicate delivery id, **Then** smoke output reports the duplicate deterministically and does not create a second approved ADR record.

### [US-2] Produce a deterministic stub ADR draft — Priority: P1
**As a** LivingADR developer, **I want** a deterministic structural-change classifier and minimal ADR draft, **so that** the drafting seam can be exercised without production classifiers or Claude.

#### Acceptance Scenarios
- **Given** the replayed event contains the stub dependency-change signal, **When** the classifier runs, **Then** it emits one `StructuralChange` and one immutable `ChangeEvidence` summary.
- **Given** the structural change exists, **When** the draft step runs, **Then** it creates one provisional `ADRDraft` with status, context, decision, consequences, alternatives placeholder, and citations to the fixture evidence.
- **Given** the draft is generated by the smoke path, **When** it is rendered, **Then** it is labeled as deterministic stub output and not production Claude-authored rationale.

### [US-3] Accept through stub HITL and persist only after approval — Priority: P1
**As a** tech lead / approver, **I want** a stub review accept action to mint an approved decision and persist an approved ADR record, **so that** the approval-bound mutation seam is proven before production review UI exists.

#### Acceptance Scenarios
- **Given** a pending stub `ADRDraft`, **When** the stub HITL accept action runs, **Then** it records an approved review decision with reviewer id, draft hash, structural-change id, and repository scope.
- **Given** no approved review decision is provided, **When** graph persistence is attempted, **Then** the smoke store rejects the mutation and reports an unauthorized mutation failure.
- **Given** the approved decision matches the reviewed draft, **When** persistence runs, **Then** exactly one approved `ADRRecord` is stored with provenance linking event, evidence, draft, and decision.

### [US-4] Answer one MCP-style why query from approved context — Priority: P1
**As an** IDE or AI-assistant user, **I want** a read-only MCP-style `answer_why` query to return the approved ADR rationale, **so that** the context delivery path is visible end to end.

#### Acceptance Scenarios
- **Given** the approved stub ADR record exists, **When** `answer_why(repository, question, code_area_id)` asks about the seeded code area, **Then** the MCP-style response includes an answer, the ADR id, and citations to approved ADR/evidence only.
- **Given** no approved ADR exists for the repository, **When** the query runs, **Then** it returns a no-approved-context response rather than reading pending drafts or raw PR evidence.

## Functional Requirements
- [FR-1] Provide a deterministic smoke fixture for one merged-PR-like event scoped by `RepositoryIdentity`.
- [FR-2] Normalize the fixture into an `SCMEvent` without provider-specific leakage beyond fixture metadata.
- [FR-3] Implement a deterministic stub classifier that emits exactly one architecture-significant `StructuralChange` for the fixture.
- [FR-4] Generate a minimal, provisional `ADRDraft` with evidence citations and explicit stub labeling.
- [FR-5] Implement a stub HITL accept path that records an approval event and derives an `ApprovedReviewDecision`-like capability.
- [FR-6] Ensure the persistence seam refuses authoritative `ADRRecord` creation without the approved decision object.
- [FR-7] Persist a stub approved `ADRRecord` and simple graph/query projection behind ports or port-shaped interfaces.
- [FR-8] Expose one read-only MCP-style `answer_why` path that reads approved context only.
- [FR-9] Produce a single smoke E2E verification command/test that demonstrates event -> draft -> approval -> persistence -> why answer.

## Non-Functional Requirements
- [NFR-1] Deterministic: smoke tests must not call Claude, GitHub, LangSmith, or external graph services.
- [NFR-2] Fast: local smoke E2E target should complete in under 10 seconds on a developer machine.
- [NFR-3] Safe by construction: no authoritative mutation path may bypass the approved-decision seam, even in stubs.
- [NFR-4] Source-of-truth discipline: code/PR fixture is evidence, approved `ADRRecord` is authoritative rationale, and graph/query data is projection.
- [NFR-5] Repository scoped: all event, draft, decision, record, and query operations include repository identity.
- [NFR-6] Local-only PoC: persistence may use local files/SQLite-compatible stubs under `var\`, matching the architecture's local deployment constraint.

## Dependencies
- Feature dependencies from feature-map: none (`depends_on: []`).
- Project dependencies: implementation assumes or creates the greenfield `living-adr` repo layout from `..\..\architecture.md#tech-stack` and `..\..\architecture.md#repositories`.

## Out of Scope
- Production GitHub App webhook signature verification or REST fetching.
- Production structural-change classifiers for dependency/schema/API changes.
- Claude client, prompts, token budgeting, or model quality evaluation.
- Production HITL UI, edit/reject flows, accessibility polish, and durable one-shot TTL enforcement beyond stub proof.
- LlamaIndex graph adapter semantics, embeddings, ranking, multi-hop retrieval, or advanced GraphRAG.
- GitHub ADR publish-back.
- Multi-repo configuration, Azure DevOps, remote MCP HTTP/OAuth, or post-PoC deployment hardening.

## Success Criteria
- [ ] One command/test replays the fixture and reaches an MCP-style why answer with cited approved ADR context.
- [ ] Duplicate fixture replay is idempotent at smoke depth.
- [ ] Attempted persistence without approved decision is covered by a failing/guard test.
- [ ] Stub outputs are explicitly labeled as deterministic smoke stubs, not production classifier/Claude output.
- [ ] All records and queries carry repository scope.
- [ ] The smoke path visibly exercises workflow-service, HITL, persistence/query port, and mcp-context-server boundaries.

## Open Questions
- None blocking planning. Production choices intentionally deferred to later features: real GitHub ingress, classifier thresholds, Claude drafting, durable approval capability semantics, graph adapter details, and MCP auth.
